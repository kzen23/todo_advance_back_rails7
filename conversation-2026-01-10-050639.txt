  ---
  1. Service Object パターン

  概要: ビジネスロジックを独立したサービスクラスに抽出する最もシンプルなパターン

  実装例

  # app/services/tasks/creator.rb
  module Tasks
    class Creator
      def initialize(params)
        @params = params
      end

      def call
        Task.create(normalized_params)
      end

      private

      def normalized_params
        @params.permit(:name, :explanation, :status, :priority)
               .merge(genre_id: @params[:genreId],
                      deadline_date: @params[:deadlineDate])
      end
    end
  end

  # app/controllers/tasks_controller.rb
  def create
    @result = Tasks::Creator.new(params).call
    tasks_all
  end

  メリット

  - ✅ シンプルで理解しやすい
  - ✅ テストが書きやすい（コントローラから独立）
  - ✅ Railsの思想に沿っている
  - ✅ 導入コストが低い

  デメリット

  - ❌ サービスが増えるとディレクトリ管理が煩雑
  - ❌ エラーハンドリングの標準化が難しい
  - ❌ サービス間の依存関係が見えにくくなる可能性

  ---
  2. Form Object パターン

  概要: パラメータ処理とバリデーションを専用クラスに集約

  実装例

  # app/forms/task_form.rb
  class TaskForm
    include ActiveModel::Model

    attr_accessor :name, :explanation, :status, :priority,
                  :genreId, :deadlineDate

    validates :name, presence: true
    validates :priority, inclusion: { in: %w[low medium high] }

    def save
      return false unless valid?

      Task.create(
        name: name,
        explanation: explanation,
        status: status,
        priority: priority,
        genre_id: genreId,
        deadline_date: deadlineDate
      )
    end

    # コントローラから直接渡せる
    def self.from_params(params)
      new(params.permit(:name, :explanation, :status, :priority,
                        :genreId, :deadlineDate))
    end
  end

  # app/controllers/tasks_controller.rb
  def create
    form = TaskForm.from_params(params)
    if form.save
      @result = form
    else
      render json: { errors: form.errors }, status: :unprocessable_entity
      return
    end
    tasks_all
  end

  メリット

  - ✅ バリデーションロジックを集約できる
  - ✅ ActiveModelの機能を活用できる（errors, validationsなど）
  - ✅ 複雑なフォームの処理に強い
  - ✅ コントローラがよりRESTfulになる

  デメリット

  - ❌ 単純なCRUDには過剰設計になりがち
  - ❌ モデルとフォームオブジェクトの責務が重複する可能性
  - ❌ 属性の二重定義が必要

  3. Interactor パターン（interactor gem使用）

  概要: ビジネスロジックを「文脈（Context）」を持つ独立した処理単位に分割

  実装例

  # Gemfile
  gem 'interactor', '~> 3.0'

  # app/interactors/create_task.rb
  class CreateTask
    include Interactor

    def call
      context.task = Task.create(task_params)

      if context.task.persisted?
        context.message = "Task created successfully"
      else
        context.fail!(error: "Failed to create task")
      end
    end

    private

    def task_params
      {
        name: context.params[:name],
        explanation: context.params[:explanation],
        status: context.params[:status],
        priority: context.params[:priority],
        genre_id: context.params[:genreId],
        deadline_date: context.params[:deadlineDate]
      }
    end
  end

  # app/interactors/normalize_task_params.rb
  class NormalizeTaskParams
    include Interactor

    def call
      context.params = context.raw_params.permit(
        :name, :explanation, :status, :priority, :genreId, :deadlineDate
      )
    end
  end

  # app/interactors/create_task_organizer.rb
  class CreateTaskOrganizer
    include Interactor::Organizer

    organize NormalizeTaskParams, CreateTask
  end

  # app/controllers/tasks_controller.rb
  def create
    result = CreateTaskOrganizer.call(raw_params: params)

    if result.success?
      @result = result.task
      tasks_all
    else
      render json: { error: result.error }, status: :unprocessable_entity
    end
  end

  メリット

  - ✅ 複雑なビジネスロジックをステップごとに分割できる
  - ✅ 各ステップのテストが容易
  - ✅ 処理の順序が明確
  - ✅ ロールバック機能がある
  - ✅ 成功/失敗の状態管理が標準化されている

  デメリット

  - ❌ 外部gemへの依存
  - ❌ 学習コストが高い
  - ❌ 小規模な処理には過剰
  - ❌ context の中身が見えにくい（魔法的）

  4. Repository パターン

  概要: データアクセスロジックを抽象化し、コントローラとモデルの間に層を作る

  実装例

  # app/repositories/task_repository.rb
  class TaskRepository
    class << self
      def all
        Task.all
      end

      def find(id)
        Task.find(id)
      end

      def create(attributes)
        Task.create(normalize_attributes(attributes))
      end

      def update(task, attributes)
        task.update(normalize_attributes(attributes))
      end

      def destroy(task)
        task.destroy
      end

      private

      def normalize_attributes(params)
        {
          name: params[:name],
          explanation: params[:explanation],
          status: params[:status],
          priority: params[:priority],
          genre_id: params[:genreId] || params[:genre_id],
          deadline_date: params[:deadlineDate] || params[:deadline_date]
        }.compact
      end
    end
  end

  # app/controllers/tasks_controller.rb
  def index
    @tasks = TaskRepository.all
    render :all_tasks
  end

  def create
    @result = TaskRepository.create(params.permit(
      :name, :explanation, :status, :priority, :genreId, :deadlineDate
    ))
    @tasks = TaskRepository.all
    render :all_tasks
  end

  def update
    TaskRepository.update(@task, params.permit(
      :name, :explanation, :status, :priority, :genreId, :deadlineDate
    ))
    @tasks = TaskRepository.all
    render :all_tasks
  end

  メリット

  - ✅ データアクセスロジックを一箇所に集約
  - ✅ 将来的にORMを変更しやすい
  - ✅ パラメータ変換ロジックを隠蔽できる
  - ✅ キャッシュ戦略を統一できる

  デメリット

  - ❌ ActiveRecordの機能を隠蔽しすぎる可能性
  - ❌ Railsの「Convention over Configuration」に反する
  - ❌ オーバーエンジニアリングになりやすい
  - ❌ コードの記述量が増える

  5. Concern + Decorator パターン（軽量アプローチ）

  概要: 最小限の変更で責務を分離する実用的なアプローチ

  実装例

  # app/controllers/concerns/task_params_normalizer.rb
  module TaskParamsNormalizer
    extend ActiveSupport::Concern

    private

    def normalized_task_params
      params.permit(:name, :explanation, :status, :priority)
            .merge(
              genre_id: params[:genreId],
              deadline_date: params[:deadlineDate]
            )
    end
  end

  # app/decorators/task_collection_decorator.rb
  class TaskCollectionDecorator
    def initialize(tasks)
      @tasks = tasks
    end

    def to_json_view
      @tasks
    end

    def self.all
      new(Task.all)
    end
  end

  # app/controllers/tasks_controller.rb
  class TasksController < ApplicationController
    include TaskParamsNormalizer

    before_action :select_task, only: [:update, :destroy, :update_status]
    skip_before_action :verify_authenticity_token

    def index
      render_tasks
    end

    def create
      @result = Task.create(normalized_task_params)
      render_tasks
    end

    def update
      @task.update(normalized_task_params)
      render_tasks
    end

    def destroy
      @task.destroy
      render_tasks
    end

    def update_status
      @task.update(status: params[:status])
      render_tasks
    end

    private

    def select_task
      @task = Task.find(params[:id])
    end

    def render_tasks
      @tasks = TaskCollectionDecorator.all.to_json_view
      render :all_tasks
    end
  end

  メリット

  - ✅ 既存のコードへの影響が最小限
  - ✅ Railsの標準機能を活用
  - ✅ 段階的にリファクタリングできる
  - ✅ 学習コストが低い
  - ✅ チームで導入しやすい

  デメリット

  - ❌ Concernの乱用で「見えない依存」が増える可能性
  - ❌ 大規模な責務分離には不十分
  - ❌ 根本的な設計改善にはならない

  ---
  推奨アプローチの選び方

  現在のプロジェクト規模なら

  推奨順位:
  1. Service Object（1番） - バランスが良く、段階的に導入可能
  2. Concern + Decorator（5番） - 最小限の変更で改善したい場合

  今後の拡張を見据えるなら

  3. Form Object（2番） - バリデーションが複雑になる予定がある場合
  4. Interactor（3番） - 複数ステップの処理が増える予定がある場合

  避けた方が良い

  5. Repository（4番） - 現時点では過剰設計の可能性が高い

  ---
  具体的にどのパターンを試してみたいか、または現在の課題感を教えていただければ、より詳細な実装サポートができます。

  実装内容

  class ServiceResult
    attr_reader :data, :errors

    def initialize(success:, data: nil, errors: [])
      @success = success
      @data = data
      @errors = Array(errors)
    end

    def success?
      @success
    end

    def failure?
      !@success
    end

    def self.success(data: nil)
      new(success: true, data: data)
    end

    def self.failure(errors:)
      new(success: false, errors: Array(errors))
    end
  end

  提供される機能

  1. 成功時の結果: ServiceResult.success(data: task)
  2. 失敗時の結果: ServiceResult.failure(errors: ['error message'])
  3. 状態確認: result.success? / result.failure?
  4. データアクセス: result.data / result.errors

  使用例（今後の実装で使用）

  # 成功時
  result = ServiceResult.success(data: task)
  result.success? # => true
  result.data     # => taskオブジェクト

  # 失敗時
  result = ServiceResult.failure(errors: ['Name is required'])
  result.failure? # => true
  result.errors   # => ['Name is required']

  module Tasks
    class CreateService
      def initialize(params)
        @params = params
      end

      def call
        task = Task.create(normalized_params)

        if task.persisted?
          ServiceResult.success(data: task)
        else
          ServiceResult.failure(errors: task.errors.full_messages)
        end
      end

      private

      def normalized_params
        {
          name: @params[:name],
          explanation: @params[:explanation],
          status: @params[:status],
          priority: @params[:priority],
          genre_id: @params[:genreId],
          deadline_date: @params[:deadlineDate]
        }.compact  # nilを除外してDBのデフォルト値を適用
      end
    end
  end

  実装のポイント

  1. compact による nil 除外
    - priority が nil の場合、ハッシュから除外される
    - DBのデフォルト値（default: 1 = medium）が自動適用される
  2. ServiceResult による統一的な結果返却
    - 成功時: ServiceResult.success(data: task)
    - 失敗時: ServiceResult.failure(errors: [...])

  3. パラメータ変換
    - genreId → genre_id
    - deadlineDate → deadline_date
